# Round 2: Act, MCP tools, and demo kit

Reviewed the working tree on `final_v1.1` (HEAD `e9d3dd2`), including untracked Act files, against `7bf3246`. Findings below are ranked. Counts: **0 critical, 2 high, 5 medium, 1 low**.

Verification: source/diff review; PowerShell AST parsing (zero syntax errors); isolated, in-memory execution of the actual ActionService methods extracted by Python AST, with fake Jira and ledger dependencies. No servers, GUI, network calls, or service lifecycle commands were run. No repository files other than this report were written. Reproduction steps below describe tests to perform, not live operations performed during this review. Windows runtime behavior was assessed statically, not by launching the kit. No unverified hypotheses are included as findings.

1. **High — Unknown Jira outcomes are reported as “Nothing was changed”; retry through a new proposal can duplicate the issue.**
   - **File:line:** `databridge/apps/internal_brain/databridge_ib/actions.py:487`, `actions.py:489`, `actions.py:492`, `actions.py:75`; `databridge/apps/internal_brain/databridge_ib/connectors/jira.py:558`; `databridge/apps/internal_brain_web/components/user/ActSheet.tsx:333`, `ActSheet.tsx:405`.
   - **Finding (confirmed):** The create request carries no stable operation identifier. A timeout, lost response, or malformed success payload is treated as a failed create and mapped to the same 409 message as a definite denial. Jira may already have committed. Separately, failure to append `ActionExecuted` after a successful create returns 503, with the proposal already consumed and no result available to replay. The frontend turns a subsequent 404 into “expired.” Closing and reopening generates a new proposal and allows the same issue to be created again. A single non-retried POST and an in-memory `used` flag prevent same-proposal double clicks, but do not provide end-to-end idempotency or recovery.
   - **Repro:** Let fake Jira append an issue, then raise a timeout. Confirm returns `Unavailable` with one issue present. Create a new proposal for the same intended operation and confirm: two issues now exist. This sequence was reproduced in memory. Also reproduced: fail only `ActionExecuted` append; confirm raises `ActionError` after creating one issue, and retrying that proposal raises `NotFound`.
   - **Fix:** Persist operation state and recoverable result, with a stable identifier carried to the source or a reconciliation mechanism. Distinguish definite failure from unknown outcome; do not promise that nothing changed for the latter. Replay a known result for repeat confirms. Block a replacement create while the original outcome is unresolved, and reconcile failed execution receipts after ledger recovery. Do not simply retry Jira POSTs.

2. **High — Windows cleanup treats unrelated processes as demo-owned and forcibly kills them.**
   - **File:line:** `databridge/scripts/demo_day.ps1:157`, `demo_day.ps1:160`, `demo_day.ps1:166`, `demo_day.ps1:170`, `demo_day.ps1:181`, `demo_day.ps1:402`, `demo_day.ps1:470`; `databridge/scripts/demo_up.sh:31`.
   - **Finding (confirmed by control flow):** The socket-owner fallback adds any `python.exe` or `node.exe` listening on the selected port, without validating its executable path or repository. The mock-platform and Next command-line matches also lack a repository check. Startup calls this cleanup automatically when a port is occupied but the expected HTTP probe fails; cleanup uses `taskkill /T /F`. Stop also delegates to the shell's unconditional port-based killer. Another development server can therefore be killed, including its descendants, despite the comments claiming repo-only ownership.
   - **Repro:** In an isolated runtime test, put an unrelated Node or Python service on 3100 that does not serve `/login`, then invoke Start. It will be classified as a stuck demo process and killed. Alternatively, run an unrelated Next instance using the same port argument: the command-line fallback can match it even without a matching socket result.
   - **Fix:** Record owned PID, creation time, executable, and canonical repository path when launching. Validate ownership before terminating, including in the delegated shell stop path. Treat an unowned port as a conflict and report it; do not kill its owner.

3. **Medium — Confirm rechecks Jira create permission but never rechecks access to the proposal's source documents.**
   - **File:line:** `databridge/apps/internal_brain/databridge_ib/actions.py:293`, `actions.py:409`, `actions.py:471`, `actions.py:481`, `actions.py:487`.
   - **Finding (confirmed):** Source authorization happens during proposal construction. Confirmation reuses the saved description and source links, checking only the destination project's create permission. Revoking all cited documents between propose and confirm still allows a ticket built from those documents to be created. This is distinct from revoking Jira create permission, which is checked. The description contains links rather than source text, so this is not a claim that revoked document bodies are copied into Jira; it is a stale-authorization issue in the action lifecycle.
   - **Repro:** Propose while the sources are readable; revoke their read access while leaving project create permission intact; confirm. In the isolated check, setting context lookup to return `None` after proposal construction had no effect: confirm created an issue without consulting it.
   - **Fix:** Reauthorize the saved source IDs immediately before execution. If the approved source set changes, reject uniformly or require review of a regenerated proposal; do not silently execute the old payload. Record the authorization outcome and keep the confirmed digest aligned with the exact payload sent.

4. **Medium — A startup timeout leaves its launcher running, then starts a second launcher; other waits are not bounded as advertised.**
   - **File:line:** `databridge/scripts/demo_day.ps1:214`, `demo_day.ps1:225`, `demo_day.ps1:423`, `demo_day.ps1:428`, `demo_day.ps1:135`, `demo_day.ps1:515`; `databridge/scripts/demo_up.sh:115`.
   - **Finding (confirmed by control flow):** `Invoke-DemoUp` returns failure at its deadline without terminating or otherwise reconciling the process it launched. `Start-Live` then retries. If the first invocation is still building, both invocations can run `next build` against the same output directory before either starts the listener. They also share the same timestamp-derived log. `Wait-Http` counts attempts rather than elapsed seconds, so a nominal 60-second wait can take roughly 240 seconds with three-second failed probes. The offline build uses unbounded `Start-Process -Wait`.
   - **Repro:** Make the first build exceed the launcher deadline while 3100 is free. Observe that the original build continues after failure is returned and the retry can start another build. For the wait issue, use a probe that takes its full three-second timeout on every attempt.
   - **Fix:** Serialize startup/build operations with a lock. On timeout, terminate and await only the owned launcher/build work, or leave it explicitly in progress and do not retry. Use a monotonic deadline across probes and bounded build waits. Preserve already-running healthy services.

5. **Medium — A passcode loaded from `.env.ib.local` reaches the server but not the PowerShell sign-in probe or preflight.**
   - **File:line:** `databridge/scripts/demo_up.sh:57`; `databridge/scripts/demo_day.ps1:119`, `demo_day.ps1:120`, `demo_day.ps1:363`, `demo_day.ps1:444`, `demo_day.ps1:449`; `databridge/scripts/demo_preflight.py:79`; `databridge/apps/internal_brain/databridge_ib/app.py:236`.
   - **Finding (confirmed by environment flow):** The environment file is sourced inside the child Bash process. An `IB_DEMO_PASSCODE` set there is inherited by the Brain, but cannot propagate back to its PowerShell parent. Both sign-in probes use only their own process environment. A normal double-click launch with the passcode configured only in that file therefore sends no passcode, mistakes the resulting 401 for ledger unavailability, unnecessarily restarts the Brain, and fails again. In addition, the PowerShell probe interpolates the passcode into JSON without escaping, so a quote or backslash can break authentication even when the environment variable is present.
   - **Repro:** Configure a nonempty passcode in the local environment file only, with no parent-shell passcode variable. Launch Start. The service requires it, while `Test-SignIn` omits it; the restart does not repair the mismatch. No secret file was read during this review.
   - **Fix:** Supply the same configuration to the server and preflight/probe processes through a deliberate shared configuration path. Serialize the login body using `ConvertTo-Json` and UTF-8. Distinguish authentication rejection from a ledger-related 503 before restarting.

6. **Medium — Preflight can announce Hunyuan LIVE and authorize Hy3 narration when every warm answer used fallback.**
   - **File:line:** `databridge/scripts/demo_preflight.py:186`, `demo_preflight.py:193`, `demo_preflight.py:241`, `demo_preflight.py:243`; `databridge/scripts/demo_day.ps1:374`; `databridge/apps/internal_brain/databridge_ib/app.py:218`; `databridge/apps/internal_brain/databridge_ib/llm.py:113`.
   - **Finding (confirmed):** Status `models.active` means that a chain object exists, not that a provider completed an answer. Preflight translates this into “Tencent Hunyuan LIVE,” and the final verdict says “Hy3 lines are allowed.” Warm checks record each response's model, but their pass/fail decision checks only citation expectations and latency and never corrects the earlier live flag. A configured chain whose calls fail quickly can return extractive answers and still produce a green live-model verdict. A successful non-Hy3 fallback can similarly be mislabeled.
   - **Repro:** Keep the model chain configured but make provider calls fail quickly; return valid extractive answers within the time budget. Warm checks pass on citation counts and latency, while the persisted `model.live` remains true and the launcher permits Hy3 narration.
   - **Fix:** Separate configured, reachable, and actually-used model status. Derive presenter guidance from the models on successful warm responses, including fallback status. Without warm evidence, label live capability unverified rather than claiming Hy3 authored answers.

7. **Medium — An explicitly empty mock Jira create ACL grants Developers permission instead of denying everyone.**
   - **File:line:** `databridge/apps/mock_platforms/mock_platforms/state.py:270`; `databridge/apps/mock_platforms/mock_platforms/jira.py:300`.
   - **Finding (confirmed):** `proj.get("create") or {"roles": ["Developers"]}` conflates an absent create policy with an explicitly empty policy. Setting `create: {}` to remove all holders restores the default developer grant. Both the live permission check and actual mock create use this helper, so they agree on the incorrect grant and do not catch each other.
   - **Repro:** Use an active member of a project's Developers role, set that project's `create` to `{}`, and check/create an issue. Access remains allowed. In contrast, a nonempty policy containing empty holder lists denies it.
   - **Fix:** Apply the default only when the policy is absent. Interpret an explicit empty policy as no holders, and reject malformed policy types without granting access. Cover absent, empty, and populated policies separately.

8. **Low — Eviction can delete an in-flight proposal before a retryable failure releases it.**
   - **File:line:** `databridge/apps/internal_brain/databridge_ib/actions.py:418`, `actions.py:437`, `actions.py:452`, `actions.py:455`, `actions.py:477`.
   - **Finding (confirmed):** `used=True` represents both in-flight and terminal states. Any concurrent proposal creation calls `_evict`, which deletes every used proposal. If the first confirmation subsequently fails its write-ahead append, `_release` only changes the detached object's flag; it does not restore the dictionary entry. A supposedly retryable, unexpired proposal is permanently lost despite no Jira side effect. Cancellation has the same release pattern.
   - **Repro:** Take proposal A, interleave `_evict` from a second proposal, then fail A's confirmation append and release A. Retrying A returns `NotFound`. This interleaving was reproduced with the actual methods in memory.
   - **Fix:** Distinguish pending, in-flight, and terminal states. Never evict an in-flight operation; restore pending state atomically on pre-effect failure. Apply capacity and expiry policies without deleting active operations.

## Coverage and lifecycle conclusions

- The first `ActionConfirmed` append precedes the Jira create (`actions.py:473`, `actions.py:487`). Failure of that write prevents creation. The unresolved case is the post-effect receipt failure in finding 1, not reversed write-ahead order.
- `_take` holds a lock while consuming a proposal (`actions.py:447`); same-proposal double confirm cannot issue two creates in one service instance. Jira create permission revoked before its live recheck is denied (`actions.py:481`). Cancel and confirm compete for the same consume step.
- Proposals are process-local (`actions.py:241`). A recreated service returns `NotFound` for an old ID; it does not reconstruct and accidentally execute it. The UI maps that to expired (`ActSheet.tsx:405`). This is a demo continuity limitation, not independently ranked as an unsafe replay bug. Restart after an uncertain create remains covered by finding 1.
- Action lookup failures use the shared 404 handler (`app.py:467`); expected source/create denials use the shared 409 body (`app.py:469`). Uniformity is preserved, but the 409's “Nothing was changed” assertion is invalid for uncertain external outcomes. Schema-validation 422s are separate from these lookup paths.
- Reviewed the new employee/audit MCP tool mappings against map, trace, stats, verify, and tamper response producers; no additional confirmed defect found. Reviewed action event registration/counting, the draft model-chain refactor, citation-tag sealing, mock error-body changes, and the AnswerCard/ActSheet integration. The docview length guard is after its write-ahead record (`databridge/apps/internal_brain/databridge_ib/docview.py:51`).
- Root launchers quote `%~dp0` for their working directory and PowerShell script path (for example, `Start Walnut Demo.cmd:6`, `Start Walnut Demo.cmd:14`). The known spaces in this repository path do not by themselves establish a quoting failure. No live end-to-end Windows launch was performed.

## Demo risk

- **Highest priority:** do not blindly repeat a ticket create after an error; the issue may exist already (finding 1).
- Start/Stop can terminate unrelated development services; slow startup retries can overlap builds (findings 2 and 4).
- A passcode configured only in the environment file can block Start and trigger an unnecessary Brain restart (finding 5).
- Green preflight does not prove Hy3 answered; the presenter guidance can be wrong (finding 6).
- Avoid restarting the Brain with an Act proposal open: it becomes expired. Reopen the sheet for a fresh proposal only when no earlier create has an uncertain outcome.
- Read-access revocation and empty-policy revocation demonstrations can produce unexpected successful creates (findings 3 and 7).
