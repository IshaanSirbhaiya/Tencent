Reviewed only the pasted bundle; no commands, files, or browsing. Paths below are relative to `apps/internal_brain/databridge_ib/audit/` unless stated otherwise. Findings involving writable projections or external sinks explicitly require that access.

1. **[High] A key holder can launder rewritten history through a new publication — `anchor.py:publish_head`, `FileSink.latest`; `ledger.py:compare_external`** — Publication checks only internal integrity. An insider with the sealing key can rewrite previously published history, regenerate internal anchors, extend the log beyond the previous published sequence, and publish again. `latest()` selects the highest sequence; verification then compares against the attacker’s new head and passes, even though older external publications remain contradictory. **Fix:** Before accepting a publication, independently verify that the proposed history extends the last trusted external checkpoint. Preserve and check earlier checkpoints; an incompatible new publication must never supersede them.

2. **[High] Projection contents are trusted without authenticating them against the ledger — `query.py:AuditProjection.sync`, `_row`, `reconstruct`** — `sync()` compares only stored `(seq, hash)` values. Someone able to modify the projection database can preserve those values while changing `events.data`, subjects, timestamps, or `doc_events`. Audit results then misrepresent who accessed what. Forged `answer_ref` and `answer_sha256` values can also redirect reveal and defeat its integrity comparison because both reference and expected digest come from the projection. The default in-memory configuration reduces the persistent-file attack surface but does not correct this validation defect. **Fix:** Derive responses from verified ledger payloads, or validate the complete projection and its derived tables against a verified snapshot.

3. **[High] External rollback detection is not enforced on operational reads or writes — `ledger.py:AccessLedger.append`, `records`, `head`; `routes.py:_sync`** — Normal appends, projection synchronization, and publication use internal verification only. A restored log-plus-anchor backup can therefore serve audit queries and accept new records even when the external head would prove rollback. Configuring `AccessLedger.external` does not change these paths. **Fix:** Establish the trusted external checkpoint before accepting or serving ledger-dependent operations, and reject histories that do not extend it. Tie that check to the snapshot being used.

4. **[High] The supplied sinks do not establish an independently protected external authority — `anchor.py:FileSink`, `SlackWebhookSink.latest`** — `FileSink.publish()` only appends to a local file; it neither pushes a repository nor enforces append-only storage. A separate repository on the same host is insufficient against a host-level attacker. Slack verification may read only a local mirror, allowing an attacker who can rewrite that mirror and the ledger to pass verification despite contradictory Slack history. Without a mirror or reader, Slack publications cannot be verified automatically. **Fix:** Require a readable, independently administered remote checkpoint service or immutable remote storage, and verify against that remote authority. Treat local files as caches.

5. **[High] A stale external checkpoint passes despite evidence of later publication — `ledger.py:compare_external`** — `published_in_log` is checked only when `ext is None`. If the ledger records publication at sequence 100 but the sink returns an authentic matching checkpoint at sequence 20, verification succeeds. Losing or withholding newer external records therefore silently weakens protection. **Fix:** Reject an external checkpoint older than a recorded successful publication, with explicit reconciliation for publication retries and an independently retained publication watermark.

6. **[High] External verification can fail open — `ledger.py:AccessLedger.verify`; `anchor.py:verify`** — When `external.latest()` raises, `AccessLedger.verify()` adds a problem but can still return `ok=True` if the surviving ledger contains no publication marker. A missing checkpoint has the same ambiguity. Disabling or omitting the sink also permits `ok=True` without external verification. Restoring a pre-publication backup makes relying on local publication markers especially unsafe. The separate `anchor.verify()` wrapper correctly fails on reader exceptions, so behavior differs by configuration. **Fix:** Track whether external verification is required independently of the ledger; required-but-unavailable must produce failure or an explicit indeterminate status, never overall success.

7. **[High] Reveal returns content even when ledger integrity fails — `routes.py:audit_reveal`; `content.py:AnswerStore.get`** — The endpoint returns `stored.answer` even when its hash differs from the ledger digest. A content-store attacker can substitute fabricated or unrelated sensitive text, which is then disclosed under another request’s reveal. The route also never checks `stored.req_id == body.req_id`. **Fix:** Before releasing any text, verify its digest against the authoritative ledger event and verify request/reference binding. On mismatch, return a content-free integrity error and record the failure.

8. **[High] Audit traffic creates an increasingly expensive shared-ledger denial of service — `query.py:sync`; `ledger.py:append`; `routes.py:audit_events`, `audit_ask`, `audit_accessors`, `audit_verify`** — Each ordinary audit query reads and verifies the whole ledger, then appends an audit event that re-verifies the whole log and anchor history. Repeated calls both consume resources and increase every subsequent operation’s cost. A compromised compliance account can exhaust workers, memory, or ledger lock capacity and interfere with request ledgering. **Fix:** Add bounded admission, concurrency and execution budgets; use a verified incremental architecture with a protected checkpoint. A result limit does not bound verification work.

9. **[Medium] Failed audit calls are not consistently ledgered — `routes.py:make_audit_router` and endpoint handlers** — Invalid filters, invalid document IDs, blank reveal reasons, unknown reveal targets, parser failures, and query failures can exit before an audit append. Framework validation and authentication failures also have no recording mechanism shown. Thus “every audit query is itself ledgered” is not implemented by these routes. **Fix:** Record authenticated attempts before processing and record their outcomes centrally, including validation errors and failures. Define the handling of unauthenticated attempts and genuine ledger outages explicitly.

10. **[Medium] `/audit/verify` deliberately returns HTTP 200 without ledgering — `routes.py:audit_verify`** — When its append fails, the route returns the report with `ledgered=False`. This directly contradicts the stated universal ledgering requirement, even though the exception is documented locally. **Fix:** Return a failure status under the existing contract, or explicitly change the contract and use an independent durable audit channel for emergency verification access.

11. **[Medium] Failed projection updates can become permanent partial records — `query.py:apply`, `_apply_locked`, `sync`, `rebuild`; `ledger.py:append`** — `_apply_locked()` inserts the event before updating document tables. If a later statement fails, no rollback occurs, and the subscriber exception is swallowed. A subsequent successful operation can commit the partial transaction. `sync()` then sees the event’s matching sequence/hash and skips repairing its missing derived data. **Fix:** Wrap each update or rebuild in a transaction/savepoint with rollback on every exception. Mark failed projections dirty and rebuild before serving them.

12. **[Medium] Concurrent append callbacks can produce a projection that differs from chronological replay — `ledger.py:append`; `query.py:apply`, `sync`, `_apply_locked`** — The core append is ordered, but subscribers run afterward without sequence ordering. A later event can be applied before an earlier one. For example, `answer.released` can create a citation row before `retrieval.decided`; the later upsert updates only some columns, retaining the wrong sequence, timestamp, or metadata. Since both event hashes are present, synchronization does not repair this. **Fix:** Apply events in ledger-sequence order under one projection writer; detect gaps and replay from the authoritative ledger.

13. **[Medium] Structured filters are not closed or range-capped — `query.py:AuditFilter._range`, `bounded`; `routes.py:audit_events`** — `/audit/events` with no dates searches all history. An `until`-only filter has no lower bound. A `since`-only filter has no actual upper bound, including when `since` is in the future. The 500-row limit restricts output, not the search interval. **Fix:** Materialize both boundaries for every query, validate their order, and enforce the maximum interval after normalization.

14. **[Medium] Query limits do not bound response size or reconstruction work — `query.py:_docs_of`, `_row`, `reconstruct`, `accessors`** — A 500-event result can expand into an unrestricted document list for each retrieval event. `reconstruct()` loads all request events and all reveals even though reveal needs only the released-answer reference. Accessors have no time bound. Large histories or document sets can therefore create expensive queries and large responses despite the advertised cap. **Fix:** Bound document expansion, response bytes and work; paginate reconstruction and accessor history; use a minimal verified answer-reference lookup for reveal.

15. **[Medium] Request-level document aggregation loses historical distinctions — `query.py:_apply_locked`, `_docs_of`, `reconstruct`** — `doc_events` is keyed by `(req_id, doc_id)`. If a request has multiple retrieval decisions, later events overwrite decisions while leaving older sequence, metadata and timestamps. Every retrieval result then receives the same request-level document list, and reconstruction keeps only the last retrieval’s lists. The pasted wrapper does not enforce one retrieval per request. **Fix:** Store document decisions per retrieval-event sequence, or enforce the single-retrieval invariant before ledger append. Build request summaries separately.

16. **[Medium] Invalid or unrecognized NL constraints silently broaden the query — `nl_filter.py:parse_deterministic`, `parse_audit_question`** — If a document/container fails validation, the fallback drops those constraints and may search broadly. For example, a document title containing `&` becomes invalid and loses its document restriction. Completely unrecognized text also defaults to all matching recent events; an invalid model response falls back to that broad deterministic query. **Fix:** Treat invalid constraints and unrecognized intent as errors or require confirmation of the proposed filter before executing. Never automatically remove a requested scope restriction.

17. **[Medium] Valid request bodies can trigger uncaught parser exceptions — `nl_filter.py:parse_time`, `_day`, `_cap`, `parse_deterministic`; `routes.py:audit_ask`** — Inputs such as `on 2026-02-30` raise `ValueError`; very large relative periods can overflow datetime bounds. Reversed ranges exceeding 365 days are swapped only after capping, then fail validation, including in the fallback. These exceptions escape before audit ledgering. **Fix:** Validate temporal expressions, order boundaries before applying caps, catch date/arithmetic errors, and return a ledgered 422 rather than an uncaught server error.

18. **[Medium] Calendar filters include the next interval’s boundary — `nl_filter.py:parse_time`; `query.py:search`** — “Yesterday,” “last week,” “on DATE,” and similar phrases generate an upper boundary at the next interval’s midnight. SQL uses `<=`, so an event exactly at today’s midnight appears in yesterday’s results. “Before DATE” also includes the boundary it should exclude. **Fix:** Use half-open calendar intervals, `since <= timestamp < until`, and preserve explicit boundary semantics for structured filters.

19. **[Medium] Publication can succeed remotely while the API reports failure — `anchor.py:publish_head`, `SlackWebhookSink.publish`** — The remote write occurs before the local `anchor.published` event. If that append fails, the remote publication still exists. Similarly, Slack can accept the message before the mirror write fails. The operation then raises without recording the successful external side effect; retries and missing-head detection become ambiguous. **Fix:** Use stable publication IDs, idempotent remote writes, and reconciliation of remote receipts. Preserve visibility of “remote accepted, local receipt pending.”

20. **[Medium] External-head validation is incomplete and “never raises” is not guaranteed — `ledger.py:compare_external`, `AccessLedger.verify`; `anchor.py:FileSink.latest`, `_published_in_log`** — The comparator does not validate `log_id`, digest shape, timestamp, or a strictly typed positive sequence. A custom reader can supply a checkpoint for another log without identity rejection. Malformed publication sequences can also raise during integer conversion outside the guarded read. **Fix:** Validate external checkpoints and publication events with a strict schema, bind them to a unique deployment/log identity, and convert malformed input into a failed verification report.

21. **[Medium] Post-publication rollback can permanently erase evidence — `anchor.py:publish_head`; `scripts/tamper_demo.py:run_scenarios`** — Restoring the log and internal anchors to a point after the last external checkpoint is undetectable, including without the sealing key. Publishing afterward does **not** recover or detect erased records; it simply anchors the surviving branch. Thus the demo’s “not detectable until the next publication” wording is misleading, and the universal deletion/rollback claim is too strong. No scheduling or maximum-publication-age enforcement appears in this bundle. **Fix:** For zero-loss assurance, obtain an independently durable receipt before release. Otherwise state the exposure window accurately and enforce publication deadlines.

22. **[Low] Accessor results silently present truncated counts — `query.py:accessors`** — The query limits matching document/request rows to 500 and then calculates per-person totals and first/last times. The response does not disclose truncation or provide pagination, so an officer can mistake a recent subset for the complete access history. **Fix:** Return pagination and explicit truncation metadata; distinguish page counts from full-history aggregates.

23. **[Low] Negative accessor limits disable the SQL limit for internal callers — `query.py:accessors`** — `min(limit, MAX_LIMIT)` applies only an upper bound. Passing `limit=-1` produces SQLite’s unlimited-result behavior. The pasted HTTP route does not expose this parameter, so this is a helper-level defect rather than a demonstrated remote bypass. **Fix:** Validate `1 <= limit <= MAX_LIMIT` at the helper boundary.

What is correct:

- Every displayed audit endpoint uses the `compliance_officer` dependency. Assuming its documented behavior, there is no demonstrated missing route-level role check or non-compliance IDOR. Global compliance access to request/document IDs is consistent with P6.
- SQL values are parameterized; dynamic SQL fragments come from fixed code. No SQL-injection path is evident.
- The NL model receives only the question and clock. Its output goes through a closed schema; no ledger rows are passed to it here.
- Successful ordinary audit queries append before returning. Reveal requires a non-whitespace reason and appends before reading answer content.
- Answer references use cryptographic randomness, inserts refuse duplicate request IDs, and the reveal digest comparison correctly identifies content mismatch—it must enforce that result.
- UTC normalization handles ordinary offset-based timestamp comparisons correctly.
- Assuming the supplied primitive’s contract, internal hash/seal/anchor verification provides its documented protection. An independently trusted external checkpoint detects incompatible history at that checkpoint.
- The answer-generation/request-release pipeline and authentication implementation are omitted. Their end-to-end P5 behavior and role enforcement cannot be certified from this bundle.
