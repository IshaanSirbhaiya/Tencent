# gis_parcels -- schema and caveats

> SYNTHETIC FIXTURE. Generated by `../generate.py`. The Aldermoor
> Territory, its wards and every parcel below are invented.

## Coordinate reference system

`AMG-1`, a **fictional local grid**. Easting/northing are metres on that
grid. They are deliberately not latitude/longitude so that no row can be
mistaken for a real place.

## Files

| File | Rows | Notes |
|---|---:|---|
| `parcels_part*.csv` | 3,000 | one row per parcel; `parcel_id` is the join key used by `permits.applications.parcel_id` |
| `address_points_part*.csv` | 4,913 | one row per addressable unit; many-to-one onto parcels |
| `zoning_codes.csv` | 12 | code lookup |

## Columns -- `parcels_part*.csv`

| Column | Meaning |
|---|---|
| `parcel_id` | `PCL-<ward>-<serial>`. Stable. |
| `zoning_code` | joins `zoning_codes.csv` |
| `land_use` | recorded use, not a permission |
| `area_sqm` / `frontage_m` | survey values, not warranted |
| `last_survey_on` | some parcels have not been surveyed since the 1990s |
| `heritage_flag` | `Y`/`N`, not a boolean type -- a CSV, not a database |
| `flood_zone` | `none`, `zone_1`, `zone_2`, `zone_3a`, `zone_3b` |

## Why this source is T2

The GIS publishes the **current** state of every parcel and nothing else.
There is no as-at query, no change table and no soft delete: a parcel that
is merged or renumbered simply stops appearing. `snapshot(at=<past>)` must
be refused, and a citation into this source is only ever
`VERIFIED_AS_OF_CAPTURE`.

A small fraction of `permits.applications.parcel_id` values (the `PCL-XX-*`
range) resolve to nothing here. That is not a bug in the fixture: it is the
referential drift you get between two systems on different release trains,
and the adapter must report it rather than silently inner-joining it away.
